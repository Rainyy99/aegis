# Case: Nonce Protocol — server-orchestrated freemint

**Overall AEGIS verdict: BLOCK** — decided at Gate 4 (instruction channel).
Gate 2 passes cleanly; this is the case that proves *a verified contract is
not the same thing as an executable flow*.

- **Subject:** Nonce Protocol "Genesis" freemint — https://nonceprotocol.xyz/mint
- **Chain:** BNB Smart Chain (chainId 56)
- **Examined:** 27 Oct 2026 (mint window 22:00 WIB; read-only observation and
  a full manual source audit — nothing was ever executed by the agent)

## Gate-by-gate

### Gate 1 — Provenance: PASS, only after independent verification
The contract addresses first reached the agent *relayed*: project site →
a second AI agent → the user → this agent. Relayed addresses are not
evidence. Both addresses were confirmed independently on Sourcify before
any conclusion was drawn.

### Gate 2 — Contract: PASS
Full manual audit of the verified source (5,915 lines):

- The real authorization struct is `MintAuthorization` (attemptId, wallet,
  agentId, receiptHash, expiry). The brief's name for it ("StartAuthorization")
  does not exist in the source.
- The contract verifies the **project signer's** signature — never the user's.
  Anti-replay: `usedAttempts` mapping + expiry check; attempts are marked used
  *before* the mint call.
- `mint()` is `nonpayable`, `nonReentrant`, `whenNotPaused`; it requires
  `msg.sender == a.wallet` and always mints the NFT **to `a.wallet`** via
  `mintAssigned`. `MAX_PER_WALLET = 2`. Mint value is 0, enforced by
  `nonpayable`.
- **No** `transferFrom` / `permit` / `approve` / `delegatecall` / `withdraw`
  exists in the FreeMint contract. The scanner's raw counts for this address
  (approve 14×, setApprovalForAll 6×, transferFrom 12×, withdraw 1×) all live
  in the *same compilation file* but belong to other contracts —
  `NonceFreeGenesis` (a standard ERC-721) and `NonceFeeVault` /
  `NonceMarketplace`, which sit at different addresses and are never called
  by FreeMint. Raw counts flag; the audit attributes. `delegatecall`,
  `selfdestruct` and `permit`: **0** everywhere.
- Roles (`nft`, `agentGate`, `signer`, `guardian`) are immutable from the
  constructor; the only setter is `setPaused`, held by the guardian. The
  agent gate is a read-only `isAuthorized` check.

Residual on-chain risk: low. Residual risk is off-chain — see Gate 4.

### Gate 3 — Signature: FAIL
The flow asks the **user** to produce EIP-712 signatures (`NONCE MCP Sign In`,
then a mint authorization) whose payloads are generated by the project's
server *during* the session. Those signatures are delivered to the server and
are **invisible to the contract** — the contract only ever sees the project
signer's signature. A payload that (a) is authored at runtime by the
counterparty and (b) has no on-chain semantics that can be audited in advance
fails the standing signature rules (decode first; domain scoped to the
project; nothing signed whose later use cannot be verified).

### Gate 4 — Instruction channel: FAIL (decisive)
The mint page itself contains a written playbook **addressed to AI agents**:
connect to an external MCP server (`mcp.nonceprotocol.xyz`), sign the login
challenge, call `prepare_attempt` / `start_attempt`, fetch a fragment, solve
a SAT puzzle (format `nonce-logic-balanced-1536`: 1,536 variables, 33,792
clauses), `submit_artifact`, then call `mint_transaction`. Execution is
orchestrated step-by-step by the counterparty's server, with each next
payload depending on the server's previous answer — nothing about the
sequence can be verified independently before it starts.

Independent confirmation from a real mint transaction on this contract
(calldata decoded against the verified ABI): `mint((bytes32 attemptId,
address wallet, uint256 agentId, bytes32 receiptHash, uint256 expiry),
bytes signature)`. The puzzle instance and its solution **never touch the
chain** — only `receiptHash`, the fingerprint of the off-chain artifact,
does. The server verifies the artifact; the project signer then authorizes.

## Verdict

**BLOCK.** The contract is honest; the flow is not executable under AEGIS
rules. Server-orchestrated execution — where a third party's page writes the
instructions, serves the payloads, and grades the work — stays outside the
agent's autonomous scope regardless of how clean the contract audit is.

*Rule this case established:* **verified contract ≠ verified flow. Check the
channel, not just the code.**
